# Dia and Sanaga — what Dia does better, and what it takes to get there

17 November 2026. **The question:** what does the Dia browser (The Browser
Company, now part of Atlassian) do better than Sanaga 0.5.0, and what work
would bring Sanaga to that level?

> **Since this page was written** the steps of section 4 were built, the
> same day: see [section 6, "What was done"](#6-what-was-done). Sections 1
> to 5 are left as they were written, as the state before the work.

**Short answer.** Dia is ahead in four places, in this order of weight:

1. **The assistant.** Dia is a browser built around a conversation that knows
   your tabs, files, history and work apps. Sanaga has two one-shot actions
   (summarise, translate) and an extension writer. This is the whole of the
   distance that matters, and most of it can be closed.
2. **The web platform.** Dia is Chromium: every Chrome Web Store extension,
   DRM video, passkeys, and no "your browser is not supported". Sanaga is
   WebKitGTK: none of the four. This cannot be closed without changing
   engine.
3. **Reach.** macOS and Windows, sync between them with a pairing code, a
   release every week with engine fixes inside 48 hours. Sanaga is Linux
   only, syncs through a folder you set up, and has no update channel.
4. **Organisation features.** Single sign-on, device policies, audit logs, a
   bug bounty, a SOC 2 report.

Sanaga is ahead where Dia does not go at all: Linux, no account, no
subscription, a model that runs on the computer, containers, per-site
settings, the mobile simulator. Section 3 lists them; they are the reason
to close gap 1 without copying Dia's model.

## How this was done, and what it is worth

- **Sanaga:** the code was read, not the README: `src/ai.rs`,
  `src/ai_cli.rs`, `src/app/intelligence.rs`, `src/app/translate.rs`,
  `src/app/plus.rs`, `src/app/buttons.rs`, `src/history.rs`, `src/sync.rs`,
  and the four earlier audits. Each "Sanaga today" line below names where
  it comes from.
- **Dia:** public sources only — its changelog (Mac 1.57.0 and Windows
  1.6.0, both of 12 November 2026), its security, plans, apps and
  for-work pages, and reviews of autumn 2026. The list is at the end.
- **Nothing was run side by side.** Dia has no Linux build, and Sanaga was
  not built in this audit (no GTK 4 / WebKitGTK 6 here). So there is **no
  measured comparison of speed or memory** in this page, only what each
  side publishes. A line marked *(reported)* comes from a secondary source
  and was not confirmed on Dia's own pages.
- The sizes in section 4 (S, M, L, XL) are estimates for one person who
  knows the code. They are not commitments.

### 1.6 Smaller things Dia has and Sanaga lacks

Checked against `src/` (no trace found of each):

- Shortcuts the person can change.
- Tab groups inside tab groups (eight levels), pinned groups, groups named
  by themselves. (Sanaga has tree tabs when tabs are vertical.)
- Rules that send links of a site to a given profile. (Sanaga has
  containers and profiles, opened by hand.)
- Split view that remembers its layout. (Sanaga's holds two tabs:
  `split: Option<(u64, u64)>`, `src/app/mod.rs:545`.)
- "Copy address as Markdown".
- Sending a video to a television (casting); a mini player for music.
- Hand-off of a tab from a phone.

Each is S or M; none changes the picture.

## 2. Where they are level

Vertical or top tabs, pinned tabs, tab groups, split view, focus mode, tab
search and a recent-tabs switcher, floating video, sleeping tabs, profiles,
a built-in blocker of ads and trackers on by default, import from other
browsers. On these Sanaga gives nothing away.

## 4. What it takes

### The one decision to take first

Sanaga's present rule is: *a page's text only goes to a model that has no
tools*. It is right, and it is exactly what an assistant like Dia's breaks:
searching the history, opening tabs and reading mail are tools, used in the
same conversation as page text that may hold orders for the model.

To go further, the rule has to become: **the model only ever gets tools
that Sanaga itself gives it, and Sanaga decides what each may do.**

- The tools are functions in Sanaga (search the history, list the tabs,
  read a tab's text), declared to the model through the API's tool calls —
  never the tools of an assistant installed on the computer. Claude Code,
  Codex and Gemini CLI stay as they are today: Claude Code tool-less,
  the other two never given page text.
- Tools that only read are allowed. A tool that changes something (close
  tabs, fill a form, send anything) shows what it will do and waits for
  the person, every time, as the extension writer already does.
- Addresses a model writes are never opened by themselves, and never
  loaded as images (an address can carry what the model has read).
- What a tool returns from a page is marked as page content in the
  request, not mixed with the person's words.
- A private tab's rule stays: a model on the computer, or nothing.

This is Dia's own list (approved tools only, no address opened by itself,
approval before a form or a draft), and its own caveat applies: no defence
is perfect. It needs its own security review before release.

Steps 1–6 bring the assistant to Dia's level for one person on one
computer. Step 7 replaces Dia's connected apps by something more open,
without matching its list app for app: Dia's ready-made, signed-in
connections to some twenty services are a company's work (agreements with
each service, review by each), not code Sanaga can write alone.

### What stays out of reach on WebKitGTK

Chrome Web Store extensions with background workers and pop-ups, DRM
video, and being the engine sites are tested on. Three ways out, none
free:

- **Stay** on WebKitGTK and say so (today's choice): light, native, and
  these three limits for good.
- **A stand-in for extensions**: background pages run in hidden web views,
  pop-ups in small windows, the most used `chrome.*` calls rewritten in
  Sanaga. XL, never complete, and uBlock Origin's network part would still
  not work (Sanaga's own blocker covers that use).
- **Change engine** to Chromium (CEF): `src/page.rs` (2,587 lines) and
  `src/shell.rs` (2,408) rewritten, the memory advantage and the small
  package lost, an engine to rebuild and ship every week. It would make
  Sanaga a different browser.

The recommendation is to stay, and to put the work where Dia cannot
follow: Linux, no account, a model on the computer, the person's own
tools.

## 5. What not to copy

- **An account to browse.** It is the first thing Dia's critics name after
  the price.
- **Content used to improve the product by default.**
- **AI behind a counter nobody can read.** Sanaga's cost is the person's
  own key or their own computer; say so plainly in Settings.
- **A memory of the person.** Dia removed its own in September 2026
  (version 1.50) and deleted what it held. Searching the history and past
  chats, kept on the computer, does the same work and can be read and
  cleared.
- **A model choosing in the person's place** between chat and search. A
  visible line and a key are enough, and predictable.

## 6. What was done

17 November 2026, after the audit. Each line says what exists now, how it
was checked, and what is still missing. "Real window": the debug build
under a virtual display (GTK 4.14, WebKitGTK 2.52.6), driven by
`SANAGA_LIVE_TEST`, with `tools/fake-model.py` answering as the model and
logging what Sanaga sent it. 230 unit tests pass (182 before), Clippy
without a warning.

**What these checks are not.** No real model answered: Ollama's side was
tried against a stand-in that speaks its protocol; Claude's side was
written from Anthropic's documentation and tried against a stand-in that
enforces the two rules most easily broken (each tool call gets its result;
a thinking block comes back untouched) — never against the real service,
no key being at hand. How well a real model uses these tools, and how it
resists a page written to mislead it, has not been measured. And nothing
below has had a security review of its own: it needs one before release.

### The decision of section 4

Taken as proposed, and written at the top of `src/chat.rs` and
`src/app/aitools.rs`: a model only ever gets the tools Sanaga gives it.

- Claude Code is still started with no tools; Codex and Gemini CLI still
  never get a page's text. Tools go to Claude's API and to Ollama only.
- What comes from pages goes between tags that say so, in the person's
  message, never in the instructions; a page cannot close its own tag
  (tested).
- An address a model writes is never opened by itself: `open_tab` is an
  action, shown and confirmed, and takes http and https only. Answers are
  drawn as text: no link, no picture is loaded from them.
- One thing was added to the proposal: with a model **outside** the
  computer, a tool that only reads (history, tabs, favourites,
  conversations) is asked about the first time it is wanted in a
  conversation — what it returns leaves the computer. A model on the
  computer reads freely.
- Once something of a private tab is in a conversation, only a model on
  the computer answers it; such a conversation is never kept.

### Where this leaves the comparison

Of the four places where Dia was ahead: the first (the assistant) is
mostly closed for one person on one computer, with three things missing
that Dia has — subtitles, dictation, and ready-made connections to work
services (which need OAuth here, and agreements there). The other three —
the web platform, reach, organisations — are where they were, except the
administrator's switch.

Where Sanaga went past what Dia offers: a model on the computer can do all
of it offline; the person's own tool servers can be added; reading tools
ask before anything leaves the computer; nothing needs an account.
